# Packaging and update design (`ndpkg`)

## 1. Requirements

1. Every component, from the kernel collection to a ported program, is installable and upgradeable after first release.
2. Upgrades are atomic and reversible; a failed kernel upgrade never bricks the machine.
3. Packages are signed; repositories are verifiable offline; the format is plain data an agent can inspect.
4. Third-party software comes from a ports tree whose builds are packages in this format (ports.md).
5. The same machinery builds the system image, so "first install" and "upgrade" are one code path.
6. A downstream can publish its own packages and system sets on top of NeoDarwin's without forking it (downstream.md).

## 2. Two layers, one format

| Layer | Content | Unit | Install mechanism |
|---|---|---|---|
| **System set** | kernel collection, `neoboot`, base libraries, launchd, core daemons | a signed set of packages pinned by content hash, materialised as a read-only **ZFS boot environment** (dataset clone + snapshot) | `ndpkg system` clones the current BE, applies the transaction, snapshots, marks it `next` in `boot.cfg`; rollback = activate the previous BE (filesystems design §3) |
| **Packages** | everything else: services, tools, ports, downstream software | `.ndpkg` | content-addressed store `/System/Packages/<name>/<version>-<hash>/` on the `ndpool/pkg` dataset (`compression=zstd`), activated into the view by bind mounts (XNU `BINDFS`/`NULLFS`, in tree) and symlink farms |

Both layers use the same manifest, the same signature scheme and the same repository index. The system set is just a package whose payload is other packages plus an installer hook that stages a boot slot.

## 3. Package format

`name-version-arch.ndpkg` = `zstd`-compressed tar containing:

```
manifest.toml      # see below; canonical, sorted keys
manifest.sig       # Ed25519 over manifest.toml; multiple signatures allowed
files/             # payload, paths relative to package root
hooks/             # optional: pre-install, post-install, pre-remove — sandboxed, no network, declared in manifest
```

`manifest.toml` (illustrative):

```toml
schema = 1
name = "ndfuse-kext"
version = "0.3.1"
arch = "aarch64"          # or "any"
license = "BSD-2-Clause"
provides = ["kext:org.neodarwin.fuse"]
requires = ["kernel-abi = 26.1", "kext:org.neodarwin.iostorage >= 1.0"]
conflicts = []
kind = "kext"             # app | lib | service | kext | kernel-collection | system-set | port
[files]                   # path, BLAKE3 digest, mode, size — generated by nd_package
"Library/Extensions/ndfuse.kext/Contents/MacOS/ndfuse" = { blake3 = "…", mode = "0755", size = 412112 }
[hooks]
post-install = "rebuild-kext-collection"   # named hook from a fixed vocabulary, not arbitrary scripts
```

Rules: dependency ranges are semver (as built, §3.1: `name OP version`, compared as RPM compares versions); `kernel-abi` is a required constraint for anything with `kind = kext | dext`; hooks come from a fixed vocabulary implemented by `pkgd` (rebuild kext collection, register launchd job, refresh font cache, …) so a package cannot run arbitrary code as root during install.

### 3.1 As built (P2-01 checkpoint 1)

Decisions where the sketch above left room; the code is `//tools/ndsign`, `rules/package.bzl` and ndamfi's `nd_ndsign.c`.

- **Container.** One zstd frame (level 19, single-threaded, content size recorded) over a POSIX ustar archive. Members, in this order: `manifest.toml`, `manifest.sig`, then, when the package has Mach-O files, `trustcache` (a version 1 module, `docs/kernel/amfi-provider.md` §4.2) and `trustcache.grant`, then `files/<path>` sorted by bytes. Only regular files and symbolic links; mtime 0, owner `root:wheel`, modes normalised to 0755 (any execute bit) or 0644 (links 0755). The reader accepts only that form (checksums, order, no `..`, absolute, empty or duplicate paths). `hooks/` is not written yet: no hook vocabulary exists before `pkgd`.
- **Digests.** SHA-256, not BLAKE3: it is in the kernel's crypto table, in CommonCrypto, and in `//tools/trustcache`, with no new dependency; the field names say `sha256`, so a later schema can add `blake3` beside it.
- **manifest.toml.** Canonical: top-level keys sorted (`arch`, `conflicts`, `kind`, `license`, `name`, `payload-sha256`, `provides`, `requires`, `schema = 1`, `version`), arrays sorted, then `[files]` (`"path" = { mode = "0755", sha256 = "…", size = N }`, or `{ link = "target", mode = "0755" }`), then `[trust-cache]` (`entries`, `grant-sha256`, `module-sha256`). Strings are printable ASCII without `"` or `\`. A reader parses it, renders it again and requires the same bytes. **`payload-sha256`** is the SHA-256 of the canonical `[files]` table: since each line carries its file's digest, it names the payload's content, the store's `<hash>` (§2).
- **Dependencies** (P2-02). The manifest's `provides`, `requires` and `conflicts` (P2-01 already wrote them; `nd_package` has the attributes) are what the solver reads; no schema change was needed. Each entry is `name` or `name OP version`, with `OP` one of `=`, `==`, `!=`, `<`, `<=`, `>`, `>=` and single spaces around it (`"libgreet >= 1.0"`, `"kernel-abi = 26.1"`); `name` may be a capability another package `provides` (`kext:org.neodarwin.fuse`). Every package also provides its own name at its version. Versions compare as libsolv's default (RPM's `rpmvercmp`): dotted numeric segments numerically, so `1.10 > 1.9`; semver's pre-release suffixes don't order as semver says, so releases use plain dotted versions until a schema says otherwise.
- **Statements.** `manifest.sig` is not a bare signature over the file but a signed statement naming it: a bundle (§4.1) whose last document is `kind = "manifest"` with `package`, `version`, `manifest-sha256` and `issued`. `trustcache.grant` is the same with `kind = "trust-cache"`, `module-sha256` and `tc-type = "ltrs"` (XNU's `kTCTypeLTRS`, the type run-time trust caches load as). One signature per package in v1; several signers later means several bundles.
- **Verification offline** (`ndsign verify`): the manifest's bundle to a trusted root, `manifest-sha256`, the manifest's canonical form and `payload-sha256`, every member against `[files]` (no extra or missing files), the trust cache and grant against `[trust-cache]`, the grant as the kernel checks it, and both statements' `package` and `version` against the manifest.
- **nd_package** (`rules/package.bzl`): stages `trees` and `files`, runs `//tools/trustcache create` over the stage (every signed arm64 Mach-O, `trust_cache_exclude` aside), and `ndsign pack`. Output `TARGET/NAME-VERSION-ARCH.ndpkg`; output groups `trustcache` and `grant` for images. `issued` is an attribute (default 0), so nothing time-dependent enters; Ed25519 signatures are deterministic (RFC 8032), so the archive is byte-identical across builds: `//tools/ndsign:pciconf_pkg` and `pciconf_pkg_again` are compared byte for byte, and so is a re-pack of the unpacked contents.

## 4. Repositories

- A repository is a directory (local, HTTP, or a git-lfs mirror) containing `index.json` (signed), `packages/*.ndpkg`, and `keys/`.
- The index lists every package's manifest digest; clients verify `index.sig`, then each manifest against its digest, then each file against the manifest. Offline verification is complete.
- Channels: `stable`, `testing`, `nightly` are just three indexes. Pinning a channel pins a content hash.
- A **transparency log** (append-only, Merkle) records every published index; clients may require inclusion proofs (borrowed from the VectraOS distribution design; optional in v1).
- Key chain (from the plan-neo pilot's package design): root → channel → release keys with `seq`, `previous` and `expires`; a manifest hashed by its own encoding; a Bloom `have` filter for peer exchange; a written threat table. Peer-to-peer fetch ("a peer is a file server, and fetching is mounting") is a later option that maps onto `/n` unions.

### 4.1 Keys and the key chain, as built (P2-01)

- **Algorithm.** Ed25519 (RFC 8032), as §3 names. One implementation everywhere: OpenSSH's `ed25519.c` (public domain, SUPERCOP ref10 as OpenBSD maintains it, already in the tree as `@apple_openssh`), compiled unmodified through `kernel/neodarwin/amfi/nd_ed25519.c` with SHA-512 from the platform (CommonCrypto on the host, libkern's crypto table in the kernel). Not CryptoKit: its Ed25519 signatures are randomised, which would break reproducible packages, and the kernel needs the verifier in C anyway. On NeoDarwin, `ndpkg` compiles the same C (no OpenSSL dependency; §4.2). `//kernel/neodarwin/amfi:ndsign_test` checks RFC 8032's vectors 1 and 2.
- **Keys.** `ndsign keygen NAME` writes `NAME.key` (the 32-byte seed in hex, mode 0600) and `NAME.pub` (the public key in hex). A root is just a trusted public key.
- **Documents.** Canonical TOML, one `key = value` per line, keys strictly increasing, values decimal integers or `"strings"` (printable ASCII, no `"` or `\`), then a last line `signature = "<128 hex>"`: Ed25519 over `NeoDarwin ndsign 1\n` followed by every byte before that line. A **bundle** is exactly three documents separated by one empty line: a **channel** certificate issued by a root, a **release** certificate issued by the channel key, and the statement, issued by the release key.
- **Certificates** carry `expires` (Unix seconds), `issuer` and `key` (hex), `kind`, `name`, `previous`, `schema = 1`, `scope` (`*`, `prefix*` or an exact package name), `seq` and `usage` (`manifest`, `trust-cache` or both). A verifier requires each document to be signed by its issuer, the issuer chain to reach a trusted root, kinds in order, `now < expires` for both certificates, the statement's kind in both `usage`s and its `package` in both `scope`s (§7.1's scoped roots).
- **Rotation.** `seq` starts at 1; `ndsign certify --previous OLD` issues seq N+1 with `previous` = SHA-256 of the seq N certificate's bytes (same issuer, kind and name). `ndsign verify --keyring DIR` refuses a chain one of DIR's known certificates supersedes (a higher seq), conflicts with (same seq, other bytes) or that doesn't follow (seq N+1 whose `previous` isn't the known seq N). The kernel keeps no such state.
- **Test chain.** `tools/ndsign/testdata/test_keys` (README: TEST-ONLY, the private keys are public): root → channel `test` → release `test-release`, seq 1, expiring 2100-01-01, plus an unrelated `other-root`.
- **Tests.** `//tools/ndsign:ndsign_test` (30 checks): the package verifies and reproduces; another root, a forged channel, a release certificate the channel didn't issue, a key the chain doesn't certify, a release key without `trust-cache` usage, a package out of scope, an expired chain and an expired release certificate are refused; a tampered binary, manual page, manifest and trust cache, and a grant re-pointed at another module, are refused; rotation (superseded, conflicting and non-following certificates). `//kernel/neodarwin/amfi:ndsign_test` (29 checks): RFC 8032, and the package's grant checked by the kernel's C (`nd_ndsign_verify_tc_grant`): accepted for its module as `ltrs`; refused for another root, no roots, at expiry, another type or module, an edited statement or certificate, truncation and padding; documents' canonical form.

### 4.2 The run-time grant, as built (P2-01 checkpoint 2)

A package's trust cache loads at run time under the package key chain, and the kernel checks it (`docs/kernel/amfi-provider.md` §4.5 has the kernel side).

- **Kernel.** Patch 0005 builds `nd_ndsign.c` and `nd_ed25519.c` into bsd with the rest of ndamfi (OpenSSH's `ed25519.c` overlaid at `bsd/ndamfi/openssh`, compiled with `-w`); `nd_amfi_grant.c` registers the verifier with `nd_tc_set_grant_verifier()`. It accepts only `kTCTypeLTRS` ("ltrs") and calls `nd_ndsign_verify_tc_grant()` at the calendar time, logging the reason when it refuses (`ndamfi: trust-cache grant refused: untrusted root`). Ed25519's verification keeps about 10 KiB of locals, so it runs on a kernel thread of its own (a fresh 16 KiB stack) while the loader waits. The kernel's libkern has no `memchr`, so `nd_ndsign.c` has its own.
- **The root.** The boot-arg `nd_pkg_root=HEX[,HEX…]` (up to four Ed25519 public keys); no root is compiled in, so without it (or with a malformed one) every run-time load is refused. Boot-args come from neoboot's `boot.cfg` on the ESP, so a root passed this way is only as trustworthy as the boot chain, as the static trust cache is (`amfi-provider.md` §4.6): enough until the chain is verified. The later form is neoboot passing the roots in `/chosen` of the device tree, measured with the rest of the boot. `security.codesigning.neodarwin.pkg_roots` reads them back.
- **The load path.** XNU has no user entry point (AMFI's user client calls `load_trust_cache_with_type()` on Apple systems), so ndamfi adds a write-only sysctl, `security.codesigning.neodarwin.load_trust_cache`: `u32 module_len, u32 grant_len` (little-endian), the module, the grant. Root only; `load_trust_cache_with_type(kTCTypeLTRS, …)` checks the caller's `com.apple.private.pmap.load-trust-cache` = `neodarwin.trust-cache.load` itself. Errors: `EPERM` (not entitled), `EAUTH` (grant refused), `EEXIST` (loaded already), `EINVAL`.
- **`ndpkg`** (`//base/ndpkg`, Embedded Swift with a C shim, as `base/pciconf`). `ndpkg activate-trust PKG.ndpkg` unpacks the archive (libzstd, bound with `dlopen`), verifies `manifest.sig` against the roots the kernel trusts with the kernel's own C (`nd_ndsign.c` and `nd_ed25519.c` compiled into the shim, SHA-2 from libmd, since NeoDarwin has no CommonCrypto), checks `manifest-sha256`, the statement's package and version, and the manifest's `[trust-cache]` digests of the module and grant, then loads them. `ndpkg load-trust MODULE GRANT` hands a module and grant to the kernel unchecked. Per-file payload checks came with installation (P2-02, §5.1), and `activate-trust` now makes them too. Since P2-02 the entitled ndpkg is the base's `/usr/sbin/ndpkg` (§5.1), which the test boots; P2-01 had it only in the test image.
- **Test.** `//kernel:sbsa_pkg_trust_test` boots `//images:pkg_trust_root` (the session root with ndpkg, `cs_probe` re-signed as `org.neodarwin.pkg-probe` and left out of the static trust cache, its package, and wrong variants from `//tests/qemu/pkg_trust`) under enforcement with `nd_pkg_root=` the test root: the probe is refused (status 137); a grant with its signatures zeroed is refused by the kernel (`bad signature`, `EAUTH`), one chained to `other-root` too (`untrusted root`), and the other-root package by ndpkg; the good package loads (`successfully loaded trust cache of type: 4`) and the probe runs as a platform binary; a second activation says it's loaded already. `//kernel:sbsa_pkg_trust_no_root_test` boots without the boot-arg: the kernel refuses the good grant (`no package root`) and the probe stays refused.

## 5. Solver and store

- `ndpkg` embeds `libsolv` (BSD-3) for dependency resolution; the input is the manifests, the output a transaction plan written as JSON (`ndpkg plan --json`) before execution so an agent or human can review it.
- Store is content-addressed; two versions of a library coexist; `ndpkg gc` removes unreferenced entries. Activation is per-"view" (system view, per-user view) via bind mounts, which gives per-user package sets for free and lets a downstream show a process a curated package view.
- Each transaction begins with a ZFS snapshot of `ndpool/pkg`; power loss mid-transaction rolls back to the snapshot on next boot.

### 5.1 As built (P2-02)

`//base/ndpkg` (Embedded Swift, `Sources/*.swift`, over the C shim `src/nd_pkg.c` and the solver driver `src/nd_solve.c`) is the base's `/usr/sbin/ndpkg` (`//base:package_tools`), signed with two entitlements the kernel checks: `com.apple.private.pmap.load-trust-cache = neodarwin.trust-cache.load` (§4.2) and `com.apple.private.nullfs_allow` (nullfs mounts).

**The store.** `/var/db/ndpkg/store/<payload-sha256>-<name>-<version>/` holds `manifest.toml`, `manifest.sig`, `trustcache` and `trustcache.grant` (when the package has them) and `files/<path>`. `payload-sha256` (§3.1) names the content, so identical payloads share an entry and two versions coexist. A package enters the store only after `ndpkg` has verified it completely: `manifest.sig` against the roots the kernel trusts (`nd_pkg_root`, with ndamfi's own C), `manifest-sha256`, the statement's package and version, `payload-sha256` against the `[files]` table, the trust cache and grant against `[trust-cache]`, and every member against `[files]` (digest and size, link target, nothing missing or extra). It's unpacked into `store/.tmp<pid>-<entry>`, every file is read back and checked against the manifest again, modes lose their write bits, directories become 0555, and one `rename` puts the entry in place (fsync'd). The store lives in `/var/db` for now, not §2's `/System/Packages` on `ndpool/pkg`: the systems ndpkg runs on root on an HFS+ ramdisk until P3-03 and P2-03 bring root on ZFS and a dataset for it.

**Activation: nullfs plus a symlink farm** (the decision). Each active entry's `files/` is mounted with XNU's nullfs at `/var/db/ndpkg/mnt/<entry>`, `/var/db/ndpkg/active/<name>` is a symlink to it, and the live prefix `/usr/local` holds one symlink per package file, `/usr/local/<p> -> /var/db/ndpkg/active/<name>/usr/local/<p>`. Why both:
- A mount alone can't do it honestly. A bind mount puts one tree on one directory, but several packages share `/usr/local/bin`; merging them would take a stack of union mounts on `/usr/local`, one read-only layer per package, each able to shadow the others' and the base's files, and an upgrade would have to reorder the stack. And `bindfs`, XNU's plain bind mount, isn't in the SBSA kernel (`MASTER.arm64.MacOSX`'s `FILESYS_BASE` has `nullfs`, not `bindfs`).
- XNU's nullfs is App Translocation's: it forces `MNT_RDONLY | MNT_NOSUID | MNT_DONTBROWSE`, needs the `nullfs_allow` entitlement, and presents the lower directory as `<mountpoint>/d/<its last component>`, so the active link is `../mnt/<entry>/d/files`. What it gives: the store is read-only and nosuid where programs run it (root can't write through it, `touch` says `Read-only file system`), a package is reached through one name per package, and pagein and mmap pass through, so programs and their code signatures run from it.
- The farm's links name `active/<name>`, not a version, so an upgrade doesn't rewrite them: it mounts the new entry, adds links for the new version's new paths, swaps `active/<name>` with one `rename`, removes the old version's dropped paths and unmounts the old entry (a busy mount is left for `gc`). Every link a version shares with the next switches at the same instant.
- Links are only made where nothing is (or the same link is), and removed only if they're still ndpkg's; a package's paths must lie under `usr/local/` (§5's system set owns the rest), and empty directories it made below `/usr/local/<dir>` go with it.
Mounts and loaded trust caches don't survive a reboot: `ndpkg activate` reloads each installed package's trust cache from its store entry (verifying the manifest and digests again first), mounts its entry, and restores `active/` and the links. Running it at boot from launchd is a follow-up (below).

**Trust.** `ndpkg` hands the kernel a trust cache only from a package it verified, at install or upgrade, or from a store entry whose manifest it verified again (`activate`); the kernel checks the grant itself (§4.2). A package without Mach-O files has an empty trust cache (`entries = 0`), which isn't loaded.

**The solver.** libsolv 0.7.40 (`@opensuse_libsolv`, BSD-3-Clause), built with `TARGET_FLAGS` as a static library (`//base:libsolv_static`, `base/libsolv/build.sh`: `src/`'s library sources, no `ext/`, no optional features) that `swift_embedded_executable`'s new `libraries` attribute links in. `src/nd_solve.c` builds a pool from text Swift writes (`nd_pkg.h` documents it): the installed set (`@System`) from the installed manifests, the available packages from the repositories' indexes, each with its `provides`, `requires` and `conflicts`, arch `aarch64` (`any` is libsolv's `noarch`), and the jobs (`SOLVER_INSTALL`, `SOLVER_ERASE`, `SOLVER_UPDATE` by name or `name = version`, or `SOLVER_UPDATE | SOLVER_SOLVABLE_ALL`). It returns the ordered transaction (`transaction_order`), one step per line (`install`, `upgrade`, `downgrade`, `remove`), or libsolv's problem strings. A job naming nothing is a problem, not a no-op; removing a package something installed requires is refused (libsolv's problem), not cascaded. `//base/ndpkg:solve_test` runs the same C over the same libsolv on the host (15 cases: newest version, a pinned version, dependency order, a provided name, upgrade one and all, downgrade, removal, a needed dependency, a conflict, an unsatisfiable version, unknown names).

**Repositories.** A local repository is a directory of `.ndpkg` files and `index.json`, which `ndpkg index DIR` writes after verifying each package: `{"schema": 1, "packages": [{"name", "version", "arch", "file", "manifest-sha256", "provides", "requires", "conflicts"}, …]}`. The index isn't signed yet (P2-04 signs indexes); it only steers the solver. Before anything is installed, the package file is verified in full and its `manifest-sha256` must be the one the plan (from the index) names. Repositories are the `-r DIR` options, else the lines of `/etc/ndpkg/repositories`. `ndpkg install FILE.ndpkg` offers a package file to the solver directly.

**Plans.** `ndpkg plan install|remove|upgrade ARGS` prints the transaction as JSON and changes nothing:
```json
{
  "schema": 1,
  "command": "install",
  "arguments": ["greet"],
  "generation": 1,
  "actions": [
    {"action": "install", "name": "libgreet", "version": "1.0", "arch": "aarch64", "reason": "dependency", "file": "/var/ndpkg-test/repo/libgreet-1.0-aarch64.ndpkg", "manifest-sha256": "…"},
    {"action": "install", "name": "greet", "version": "1.0", "arch": "aarch64", "reason": "explicit", "file": "…", "manifest-sha256": "…"}
  ]
}
```
Actions are `install` (with `reason`, `explicit` or `dependency`), `upgrade` and `downgrade` (with `from`) and `remove`, in the solver's order. `ndpkg apply PLAN` executes a saved plan only if the installed state is still at the plan's `generation`; `install`, `remove` and `upgrade` (no arguments: everything) plan and apply at once, and `--json` prints the plan first. Applying: (1) verify every new package and add it to the store; (2) check file conflicts (another package's path, or a file no package owns); (3) load the new trust caches; (4) activate in the solver's order; (5) commit the state.

**State.** `/var/db/ndpkg/installed` is a symlink to `generations/<N>`, which holds §8's `<name>/{manifest,files,state}` for each installed package (`state`: `entry`, `name`, `reason`, `version`, in the canonical `key = "value"` form). A transaction writes generation N+1 in full beside it and swaps the link with one `rename`, so a reader sees the old set or the new one; generation N is kept (the state before the last transaction), older ones are deleted, and `ndpkg gc` removes store entries neither names (and unmounts what nothing active uses). `/var/db/ndpkg/lock` (`flock`) serialises the commands that change anything; they need root.

**Commands.** `install`, `remove`, `upgrade`, `plan`, `apply`, `list` and `info` (both with `--json`), `index`, `activate`, `gc`, and P2-01's `activate-trust` and `load-trust`; `ndpkg.8` documents them.

**Test** (`//tests/qemu/ndpkg:sbsa_ndpkg_test`, //images:ndpkg_root: the session root with an empty store, the test packages of `//tests/qemu/ndpkg` (hello 1.0 and 2.0, each a Mach-O with a trust cache; greet, a script requiring `libgreet >= 1.0`; libgreet, a data file; all signed with the TEST-ONLY chain) in `/var/ndpkg-test/repo`, a tampered hello 1.0 beside them, and `nd_pkg_root` = the test root under enforcement). `ndpkg index` the repository; `plan install hello=1.0` to a file, its JSON checked, then `apply` it: the kernel accepts the grant, hello prints `hello from package hello 1.0`, and writing through the store fails (`Read-only file system`); `plan install greet` lists libgreet as a dependency first, `install greet` installs both and greet prints libgreet's greeting; unmounting greet's entry (as a reboot would) breaks it until `ndpkg activate`; `plan upgrade` shows hello 1.0 → 2.0, `upgrade` loads 2.0's trust cache and hello prints 2.0; `list --json` and `info`; `plan remove libgreet` is refused (greet requires it); `plan remove hello`, then `remove hello`: `/usr/local/bin/hello` and `active/hello` are gone; the tampered package is refused (`files/usr/local/bin/hello does not match the manifest`); `gc` removes hello 1.0's entry. P2-01's `//kernel:sbsa_pkg_trust_test` and `sbsa_pkg_trust_no_root_test` now run the base's `/usr/sbin/ndpkg`.

**Not yet** (resume notes): ~~a launchd job running `ndpkg activate` at boot~~ (done in P2-03: `ndpkg boot`, §6.1; it needs `nd_pkg_root` in every boot that has packages); §5's ZFS snapshot of `ndpool/pkg` per transaction (§5.2) and §2's `/System/Packages` path: until then an interrupted transaction leaves the committed state at the old generation, and `ndpkg activate` re-links what it names, but the farm may keep links the new generation would have added; per-user views (a nullfs mount per view); `rollback` to the kept generation, `search`, `verify`; `pkgd`'s JSON-lines log at `/var/log/ndpkg.log`; hooks; signed, remote repositories (P2-04); autoremove of unneeded dependencies (the `reason` field is recorded for it).

### 5.2 The store on ZFS (P2-03)

On a root on ZFS the whole ndpkg database, `/var/db/ndpkg` (store, generations, `installed`, mounts, `active/`, and §6.1's `system/`), is the dataset **`ndpool/pkg`** (`compression=lz4`), shared by every boot environment, as §2 asks; the path stays §5.1's, not `/System/Packages`, so nothing above changed. `zfs_root_disk`'s new `datasets` attribute (`tools/zfsimage/mkpool.sh`) creates it in the build guest before the copy, so the image's `/private/var/db/ndpkg` lands in it. Nothing mounts non-root datasets at boot yet (no `zfs mount -a` job), so **ndpkg mounts its own**: every ndpkg run as root, on a ZFS root whose `/var/db/ndpkg` isn't a mount point, runs `zfs mount POOL/pkg` if the dataset exists. Images without a ZFS root keep `/var/db/ndpkg` in the root as before. Consequence: user packages (`/usr/local`) are shared state across BEs while the symlink farm in `/usr/local` belongs to each BE; `ndpkg activate` at boot re-creates the links the state names, but a BE rolled back to may keep dangling links of packages removed after it was cloned. Not done: a snapshot of `ndpool/pkg` per transaction (§5); `ndpool/home` and `var` datasets.

## 6. Kernel and kext updates

1. `ndpkg system upgrade` clones the active boot environment to a new dataset, installs the new `kernel` and kexts into it, runs `kcgen` → `kc.boot` written to the ESP under `/EFI/NeoDarwin/be/<be-name>/`, then snapshots the BE and marks it `next` in `boot.cfg`.
2. `neoboot` reads `boot.cfg` (`default`, `next`, `tries`). It decrements `tries`; once userland reaches `launchd` and `pkgd` marks boot-ok, `tries` is reset and `next` becomes `default`. Three failed tries boot the previous BE automatically.
3. Kexts declare `kernel-abi`; a kext for the wrong ABI cannot enter a collection. ABI is bumped only when the kernel's export list changes incompatibly (checked by `exports_list` diff in CI).
4. Auxiliary (non-boot) kexts and dexts are loaded post-boot from an `aux` collection rebuilt the same way; no dynamic single-kext loading on ARM64 (XNU disables it when booted from a fileset).

### 6.1 As built (P2-03): system sets as boot environments

**The decision: per-BE kernels on the ESP, chosen by neoboot.** A BE's kernel collection must be the one neoboot loads, and neoboot runs before ZFS: it reads FAT, not the pool (P3-06), and the BE choice of P3-03 (`org.neodarwin:bootonce`, `bootfs`) happens inside zfs.kext, after the kernel is loaded. Of the options:
- (a) neoboot reading the kernel from the BE (P3-06, FreeBSD's `libsa/zfs`) is the end state but a project of its own;
- (b) one kernel on the ESP for every BE can't be honest: a fallback would boot the old BE on the new kernel, and a broken kernel would break every BE;
- **(c), chosen:** the ESP holds each BE's collection and static trust cache, `\NeoDarwin\be\<BE>\{kernelcache,trustcache}`, and neoboot chooses the BE: `\NeoDarwin\bootonce` if present (it **deletes the file before loading anything**, with UEFI's `EFI_FILE_PROTOCOL.Delete`, so the try is one-shot whatever fails after it: a kernel that panics or hangs, a root that never mounts, a userland that never confirms), else `be=` in `boot.cfg`. It loads that BE's files, drops `be=` from the command line and rewrites `rd=zfs:POOL` as `rd=zfs:POOL/ROOT/<BE>`, so the kernel and the root always come from the same BE (`boot/neoboot/Sources/BootEnvironment.swift`). Without `be=` or `bootonce` nothing changes (every other image, P3-03's tests).
- **Not safe for real hardware yet (2026-10-07).** The ESP is rewritten whole and in place, and the write isn't atomic. A power loss or crash during `ndpkg system upgrade`/`confirm`/`rollback` can leave the ESP unreadable, and the machine unbootable until it's repaired from external media. Before any board runs this, the write needs one of: two ESPs written alternately with neoboot choosing the valid one; or P3-06, neoboot reading each BE's kernel from ZFS, which retires the ESP mirror.
- **Writing the ESP from userland** without msdosfs (P3-04): `makefs -t msdos` is in the base (FreeBSD's, P4-21), so the ESP is **derived state, written whole**. Its mirror is `/var/db/ndpkg/system/esp` on `ndpool/pkg` (`EFI/BOOT/BOOTAA64.EFI`, `NeoDarwin/boot.cfg`, `NeoDarwin/be/<BE>/…`, `NeoDarwin/bootonce`); ndpkg makes a FAT image of it the partition's size and writes it over partition 1 of the pool's disk (`zpool list -vHP`), only if that partition already holds a FAT file system of that size, then `fsync` and `DKIOCSYNCHRONIZECACHE` (`nd_pkg_write_esp`). The release image's mirror and ESP are made from the same files at build time. What remains: the write isn't atomic (power loss mid-write leaves an unbootable ESP; a second ESP, or P3-04's msdosfs writing files in place, fixes that), userland can't read the ESP back (`bootonce` consumed by neoboot is inferred: every boot uses it up), and the ESP has to hold every BE's collection (`esp_size`, new in `gpt_disk_image`: 160 MB for the test image, about six 23 MB collections).
- So §6's `next`/`tries` in `boot.cfg` became `bootonce` (one try, not three) and `be=`, and the pool's `bootonce` (P3-03) isn't used on such disks: a try the kext consumed but the kernel never reached would boot the old kernel on the new BE. `ndpkg system` still sets `bootfs` with `ndbectl activate`, so `ndbectl list` and a `boot.cfg` without `be=` agree.

**System sets.** A set is a signed package of kind `system-set` (no files) whose `requires` pin its components exactly, `name = version` (anything else is refused), so no solver runs: a `kernel-collection` package (`System/Library/Kernels/kernelcache`, and `System/Library/Kernels/trustcache`, the static trust cache of the base it was built with) and packages of the new kind **`system`** (the userland base; `rules/package.bzl` and ndsign accept it). System packages may install anywhere but `/dev` and `/var/db/ndpkg` (`payloadPathOK(system:)`), `ndpkg install`/`apply` refuse them, and they don't go through the store: `ndpkg system upgrade` verifies each fully (`openPackage`, the index's `manifest-sha256`) and writes its files straight into the new BE, each beside and renamed over, with its **receipt** in the BE, `/System/Library/Receipts/ndpkg/<name>/` (`manifest.toml`, `manifest.sig`, `trustcache`, `trustcache.grant`): a BE carries its own set and rolls back with it, and every read of a receipt verifies its signature again. Files the old version had and the new hasn't are removed, and so are packages the new set dropped. A release image is built the same way: `nd_system_tree` (`rules/package.bzl`) verifies packages with `ndsign unpack` (which now writes `manifest.sig` too) and lays out their files and receipts as an image tree.

**Commands** (`base/ndpkg/Sources/System.swift`, `ndpkg-system.8`):
- `ndpkg [-r REPO] system upgrade [VERSION]`: the booted set's name, the newest version in the repositories (or VERSION); every package verified first; `ndbectl create <set>-<version>` from the booted BE, `ndbectl mount`, the packages installed, `ndbectl umount`; the kernel package's collection and trust cache into the mirror's `be/<BE>/`; `bootonce` = the BE; the ESP written. Reboot to try it.
- `ndpkg system confirm`: if the booted BE is the pending try, `ndbectl activate` it (`bootfs`), make it `be=`, keep the old default as `previous`, write the ESP; if another BE booted, the try failed and is reported. Either way the try is cleared.
- `ndpkg system rollback`: `previous` becomes the default again (`ndbectl activate`, `be=`, the ESP), and the default it replaced becomes `previous`.
- `ndpkg system status [--json]` (booted BE and set, default, try, previous, the set's packages: `freebsd-version`'s job) and `list` (each BE: `N` booted, `D` default, `T` pending try, `P` rollback target, and its set, from `/var/db/ndpkg/system/sets/<BE>`).
- **`ndpkg boot`**, the launchd job `org.neodarwin.ndpkg.boot` (`RunAtLoad`, log `/var/log/ndpkg-boot.log`) in the base's `package_tools`: mounts `ndpool/pkg`, loads the booted BE's system packages' trust caches (receipts verified again; needs `nd_pkg_root`), `ndpkg activate` (§5.1's follow-up), then `system confirm`. "Reached multi-user" means launchd ran its jobs; a userland too broken for that never confirms, and the next boot falls back.
- `ndbectl` (P3-03) is now in the base, `/sbin/ndbectl` with `ndbectl.8`.

**Test** (`//tests/qemu/ndsystem:sbsa_ndsystem_test`, six boots of one copy of `//images:ndsystem_disk`, the "release image": a root on ZFS installed from set 1 with a local repository holding sets 2 and 3; packages signed with the TEST-ONLY chain, `nd_pkg_root` the test root). Set N pins `kernel N` and `nd-release N` (a Mach-O printing `nd-release: system set N`; 1 is in the base's static trust cache, 2 and 3 bring their own). Kernel 1 is `sbsa_kc`, kernel 2 `sbsa_marker_kc` (plus `NDSwiftTrial.kext`, which logs `NDSwiftTrial: starting`), kernel 3 `sbsa_kernel_only_kc` (no zfs.kext: broken on purpose). Boots: (1) `default`, set 1: `system upgrade 2` creates `neodarwin-system-2`, installs kernel 2 and nd-release 2, writes the ESP, `list` shows the try; (2) neoboot takes and deletes the try, the marker logs, the boot job loads nd-release 2's trust cache and confirms, nd-release prints 2; (3) set 2 is the default and boots again; `system upgrade` takes the newest, set 3; (4) the try boots kernel 3: `rooting via ZFS: ndpool/ROOT/neodarwin-system-3`, then nothing reads the pool (no `zfs_boot_probe_disk`), and once IOKit has matched every driver the kernel is still waiting for its root, with no login; the test stops QEMU there, as a watchdog would reset the board; (5) neoboot falls back to set 2 (the try was used up), the boot job reports the failed try, `system rollback`; (6) `default`, set 1, no marker.

**Not yet** (resume notes): kext packages and the auxiliary collection (§6 item 4; `kldload`/`kldconfig`/`kldunload`'s `ndpkg-kext.8` rows stay open): a set's kexts come only inside its kernel collection package, built by Bazel; rebuilding a collection on the machine needs `kcgen` in the base. `ndpkg system destroy` (old BEs and their ESP kernels; `ndbectl destroy` leaves the mirror's `be/<BE>`), and a check that the ESP has room before writing. Signed indexes (P2-04): the set is found by name in an unsigned index, though every package is verified. Read-only system BEs (`readonly=on`, filesystems.md §8.6). The ESP write's atomicity (above). neoboot reading the kernel from the BE (P3-06) retires the mirror's `be/`.

## 7. Third-party software: the ports tree

Third-party software comes from NeoDarwin's own ports tree (`ports.md`, decision 2026-09-29). A port is a recipe; building it produces an `.ndpkg` with `kind = "port"` and provenance (origin, recipe commit, upstream version, distfile digests, licence). Ports have their own repository index (`ports`) and key, the base never depends on a port, and GPL software ships only this way. FreeBSD ports and pkgsrc are import sources for recipes, not runtime dependencies.

## 7.1 Trust roots for downstreams

`ndpkg` can trust several key-chain roots. Each root is scoped to the package names or origins it may sign: NeoDarwin's root signs the base and the ports index; a downstream's root signs the downstream's packages and system sets; a machine's local key signs packages built there with `ndports`. A root cannot sign outside its scope, so adding a downstream repository cannot replace a base package (`downstream.md` §3).

## 8. Command surface and files

(As built in P2-02 and P2-03: §5.1's subset, with `apply`, `list`, `index` and `activate`; `ndpkg system status|list|upgrade|confirm|rollback` and `ndpkg boot`, §6.1, where `switch` is `upgrade VERSION`.) `ndpkg install|remove|upgrade|rollback|search|info|verify|gc|plan`, `ndpkg system status|switch|rollback`. Every command has `--json`. The installed state is plain files under `/var/db/ndpkg/installed/<name>/{manifest,files,state}`, and `pkgd` logs transactions as JSON lines to `/var/log/ndpkg.log`. A downstream can serve the same information in its own form (Magi publishes it under `/n/sys/pkg`).

## 9. Bootstrapping order

P2-01 format + `nd_package` rule → P2-02 store + activation → P2-03 system sets as ZFS boot environments (needs P3-03 root on ZFS) → P2-04 repositories + signing → P2-05 ports tree (ports.md §8) → P2-10 and P2-11 importers and bulk builds → P2-09 transparency log (optional).
