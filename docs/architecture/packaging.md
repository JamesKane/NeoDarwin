# Packaging and update design (`ndpkg`)

## 1. Requirements

1. Every component, from the kernel collection to a ported program, is installable and upgradeable after first release.
2. Upgrades are atomic and reversible; a failed kernel upgrade never bricks the machine.
3. Packages are signed; repositories are verifiable offline; the format is plain data an agent can inspect.
4. Third-party software comes from a ports tree whose builds are packages in this format (ports.md).
5. The same machinery builds the system image, so "first install" and "upgrade" are one code path.
6. A downstream can publish its own packages and system sets on top of NeoDarwin's without forking it (downstream.md).

## 2. Two layers, one format

| Layer | Content | Unit | Install mechanism |
|---|---|---|---|
| **System set** | kernel collection, `neoboot`, base libraries, launchd, core daemons | a signed set of packages pinned by content hash, materialised as a read-only **ZFS boot environment** (dataset clone + snapshot) | `ndpkg system` clones the current BE, applies the transaction, snapshots, marks it `next` in `boot.cfg`; rollback = activate the previous BE (filesystems design §3) |
| **Packages** | everything else: services, tools, ports, downstream software | `.ndpkg` | content-addressed store `/System/Packages/<name>/<version>-<hash>/` on the `ndpool/pkg` dataset (`compression=zstd`), activated into the view by bind mounts (XNU `BINDFS`/`NULLFS`, in tree) and symlink farms |

Both layers use the same manifest, the same signature scheme and the same repository index. The system set is just a package whose payload is other packages plus an installer hook that stages a boot slot.

## 3. Package format

`name-version-arch.ndpkg` = `zstd`-compressed tar containing:

```
manifest.toml      # see below; canonical, sorted keys
manifest.sig       # Ed25519 over manifest.toml; multiple signatures allowed
files/             # payload, paths relative to package root
hooks/             # optional: pre-install, post-install, pre-remove — sandboxed, no network, declared in manifest
```

`manifest.toml` (illustrative):

```toml
schema = 1
name = "ndfuse-kext"
version = "0.3.1"
arch = "aarch64"          # or "any"
license = "BSD-2-Clause"
provides = ["kext:org.neodarwin.fuse"]
requires = ["kernel-abi = 26.1", "kext:org.neodarwin.iostorage >= 1.0"]
conflicts = []
kind = "kext"             # app | lib | service | kext | kernel-collection | system-set | port
[files]                   # path, BLAKE3 digest, mode, size — generated by nd_package
"Library/Extensions/ndfuse.kext/Contents/MacOS/ndfuse" = { blake3 = "…", mode = "0755", size = 412112 }
[hooks]
post-install = "rebuild-kext-collection"   # named hook from a fixed vocabulary, not arbitrary scripts
```

Rules: dependency ranges are semver; `kernel-abi` is a required constraint for anything with `kind = kext | dext`; hooks come from a fixed vocabulary implemented by `pkgd` (rebuild kext collection, register launchd job, refresh font cache, …) so a package cannot run arbitrary code as root during install.

### 3.1 As built (P2-01 checkpoint 1)

Decisions where the sketch above left room; the code is `//tools/ndsign`, `rules/package.bzl` and ndamfi's `nd_ndsign.c`.

- **Container.** One zstd frame (level 19, single-threaded, content size recorded) over a POSIX ustar archive. Members, in this order: `manifest.toml`, `manifest.sig`, then, when the package has Mach-O files, `trustcache` (a version 1 module, `docs/kernel/amfi-provider.md` §4.2) and `trustcache.grant`, then `files/<path>` sorted by bytes. Only regular files and symbolic links; mtime 0, owner `root:wheel`, modes normalised to 0755 (any execute bit) or 0644 (links 0755). The reader accepts only that form (checksums, order, no `..`, absolute, empty or duplicate paths). `hooks/` is not written yet: no hook vocabulary exists before `pkgd`.
- **Digests.** SHA-256, not BLAKE3: it is in the kernel's crypto table, in CommonCrypto, and in `//tools/trustcache`, with no new dependency; the field names say `sha256`, so a later schema can add `blake3` beside it.
- **manifest.toml.** Canonical: top-level keys sorted (`arch`, `conflicts`, `kind`, `license`, `name`, `payload-sha256`, `provides`, `requires`, `schema = 1`, `version`), arrays sorted, then `[files]` (`"path" = { mode = "0755", sha256 = "…", size = N }`, or `{ link = "target", mode = "0755" }`), then `[trust-cache]` (`entries`, `grant-sha256`, `module-sha256`). Strings are printable ASCII without `"` or `\`. A reader parses it, renders it again and requires the same bytes. **`payload-sha256`** is the SHA-256 of the canonical `[files]` table: since each line carries its file's digest, it names the payload's content, the store's `<hash>` (§2).
- **Statements.** `manifest.sig` is not a bare signature over the file but a signed statement naming it: a bundle (§4.1) whose last document is `kind = "manifest"` with `package`, `version`, `manifest-sha256` and `issued`. `trustcache.grant` is the same with `kind = "trust-cache"`, `module-sha256` and `tc-type = "ltrs"` (XNU's `kTCTypeLTRS`, the type run-time trust caches load as). One signature per package in v1; several signers later means several bundles.
- **Verification offline** (`ndsign verify`): the manifest's bundle to a trusted root, `manifest-sha256`, the manifest's canonical form and `payload-sha256`, every member against `[files]` (no extra or missing files), the trust cache and grant against `[trust-cache]`, the grant as the kernel checks it, and both statements' `package` and `version` against the manifest.
- **nd_package** (`rules/package.bzl`): stages `trees` and `files`, runs `//tools/trustcache create` over the stage (every signed arm64 Mach-O, `trust_cache_exclude` aside), and `ndsign pack`. Output `TARGET/NAME-VERSION-ARCH.ndpkg`; output groups `trustcache` and `grant` for images. `issued` is an attribute (default 0), so nothing time-dependent enters; Ed25519 signatures are deterministic (RFC 8032), so the archive is byte-identical across builds: `//tools/ndsign:pciconf_pkg` and `pciconf_pkg_again` are compared byte for byte, and so is a re-pack of the unpacked contents.

## 4. Repositories

- A repository is a directory (local, HTTP, or a git-lfs mirror) containing `index.json` (signed), `packages/*.ndpkg`, and `keys/`.
- The index lists every package's manifest digest; clients verify `index.sig`, then each manifest against its digest, then each file against the manifest. Offline verification is complete.
- Channels: `stable`, `testing`, `nightly` are just three indexes. Pinning a channel pins a content hash.
- A **transparency log** (append-only, Merkle) records every published index; clients may require inclusion proofs (borrowed from the VectraOS distribution design; optional in v1).
- Key chain (from the plan-neo pilot's package design): root → channel → release keys with `seq`, `previous` and `expires`; a manifest hashed by its own encoding; a Bloom `have` filter for peer exchange; a written threat table. Peer-to-peer fetch ("a peer is a file server, and fetching is mounting") is a later option that maps onto `/n` unions.

### 4.1 Keys and the key chain, as built (P2-01)

- **Algorithm.** Ed25519 (RFC 8032), as §3 names. One implementation everywhere: OpenSSH's `ed25519.c` (public domain, SUPERCOP ref10 as OpenBSD maintains it, already in the tree as `@apple_openssh`), compiled unmodified through `kernel/neodarwin/amfi/nd_ed25519.c` with SHA-512 from the platform (CommonCrypto on the host, libkern's crypto table in the kernel). Not CryptoKit: its Ed25519 signatures are randomised, which would break reproducible packages, and the kernel needs the verifier in C anyway. On NeoDarwin, `ndpkg` compiles the same C (no OpenSSL dependency; §4.2). `//kernel/neodarwin/amfi:ndsign_test` checks RFC 8032's vectors 1 and 2.
- **Keys.** `ndsign keygen NAME` writes `NAME.key` (the 32-byte seed in hex, mode 0600) and `NAME.pub` (the public key in hex). A root is just a trusted public key.
- **Documents.** Canonical TOML, one `key = value` per line, keys strictly increasing, values decimal integers or `"strings"` (printable ASCII, no `"` or `\`), then a last line `signature = "<128 hex>"`: Ed25519 over `NeoDarwin ndsign 1\n` followed by every byte before that line. A **bundle** is exactly three documents separated by one empty line: a **channel** certificate issued by a root, a **release** certificate issued by the channel key, and the statement, issued by the release key.
- **Certificates** carry `expires` (Unix seconds), `issuer` and `key` (hex), `kind`, `name`, `previous`, `schema = 1`, `scope` (`*`, `prefix*` or an exact package name), `seq` and `usage` (`manifest`, `trust-cache` or both). A verifier requires each document to be signed by its issuer, the issuer chain to reach a trusted root, kinds in order, `now < expires` for both certificates, the statement's kind in both `usage`s and its `package` in both `scope`s (§7.1's scoped roots).
- **Rotation.** `seq` starts at 1; `ndsign certify --previous OLD` issues seq N+1 with `previous` = SHA-256 of the seq N certificate's bytes (same issuer, kind and name). `ndsign verify --keyring DIR` refuses a chain one of DIR's known certificates supersedes (a higher seq), conflicts with (same seq, other bytes) or that doesn't follow (seq N+1 whose `previous` isn't the known seq N). The kernel keeps no such state.
- **Test chain.** `tools/ndsign/testdata/test_keys` (README: TEST-ONLY, the private keys are public): root → channel `test` → release `test-release`, seq 1, expiring 2100-01-01, plus an unrelated `other-root`.
- **Tests.** `//tools/ndsign:ndsign_test` (30 checks): the package verifies and reproduces; another root, a forged channel, a release certificate the channel didn't issue, a key the chain doesn't certify, a release key without `trust-cache` usage, a package out of scope, an expired chain and an expired release certificate are refused; a tampered binary, manual page, manifest and trust cache, and a grant re-pointed at another module, are refused; rotation (superseded, conflicting and non-following certificates). `//kernel/neodarwin/amfi:ndsign_test` (29 checks): RFC 8032, and the package's grant checked by the kernel's C (`nd_ndsign_verify_tc_grant`): accepted for its module as `ltrs`; refused for another root, no roots, at expiry, another type or module, an edited statement or certificate, truncation and padding; documents' canonical form.

### 4.2 The run-time grant, as built (P2-01 checkpoint 2)

A package's trust cache loads at run time under the package key chain, and the kernel checks it (`docs/kernel/amfi-provider.md` §4.5 has the kernel side).

- **Kernel.** Patch 0005 builds `nd_ndsign.c` and `nd_ed25519.c` into bsd with the rest of ndamfi (OpenSSH's `ed25519.c` overlaid at `bsd/ndamfi/openssh`, compiled with `-w`); `nd_amfi_grant.c` registers the verifier with `nd_tc_set_grant_verifier()`. It accepts only `kTCTypeLTRS` ("ltrs") and calls `nd_ndsign_verify_tc_grant()` at the calendar time, logging the reason when it refuses (`ndamfi: trust-cache grant refused: untrusted root`). Ed25519's verification keeps about 10 KiB of locals, so it runs on a kernel thread of its own (a fresh 16 KiB stack) while the loader waits. The kernel's libkern has no `memchr`, so `nd_ndsign.c` has its own.
- **The root.** The boot-arg `nd_pkg_root=HEX[,HEX…]` (up to four Ed25519 public keys); no root is compiled in, so without it (or with a malformed one) every run-time load is refused. Boot-args come from neoboot's `boot.cfg` on the ESP, so a root passed this way is only as trustworthy as the boot chain, as the static trust cache is (`amfi-provider.md` §4.6): enough until the chain is verified. The later form is neoboot passing the roots in `/chosen` of the device tree, measured with the rest of the boot. `security.codesigning.neodarwin.pkg_roots` reads them back.
- **The load path.** XNU has no user entry point (AMFI's user client calls `load_trust_cache_with_type()` on Apple systems), so ndamfi adds a write-only sysctl, `security.codesigning.neodarwin.load_trust_cache`: `u32 module_len, u32 grant_len` (little-endian), the module, the grant. Root only; `load_trust_cache_with_type(kTCTypeLTRS, …)` checks the caller's `com.apple.private.pmap.load-trust-cache` = `neodarwin.trust-cache.load` itself. Errors: `EPERM` (not entitled), `EAUTH` (grant refused), `EEXIST` (loaded already), `EINVAL`.
- **`ndpkg`** (`//base/ndpkg`, Embedded Swift with a C shim, as `base/pciconf`). `ndpkg activate-trust PKG.ndpkg` unpacks the archive (libzstd, bound with `dlopen`), verifies `manifest.sig` against the roots the kernel trusts with the kernel's own C (`nd_ndsign.c` and `nd_ed25519.c` compiled into the shim, SHA-2 from libmd, since NeoDarwin has no CommonCrypto), checks `manifest-sha256`, the statement's package and version, and the manifest's `[trust-cache]` digests of the module and grant, then loads them. `ndpkg load-trust MODULE GRANT` hands a module and grant to the kernel unchecked. Per-file payload checks belong with installation (P2-02). ndpkg is installed only in the test image, signed there with the entitlement (`//tests/qemu/pkg_trust:ndpkg`): an entitled loader belongs in the base with P2-02's store.
- **Test.** `//kernel:sbsa_pkg_trust_test` boots `//images:pkg_trust_root` (the session root with ndpkg, `cs_probe` re-signed as `org.neodarwin.pkg-probe` and left out of the static trust cache, its package, and wrong variants from `//tests/qemu/pkg_trust`) under enforcement with `nd_pkg_root=` the test root: the probe is refused (status 137); a grant with its signatures zeroed is refused by the kernel (`bad signature`, `EAUTH`), one chained to `other-root` too (`untrusted root`), and the other-root package by ndpkg; the good package loads (`successfully loaded trust cache of type: 4`) and the probe runs as a platform binary; a second activation says it's loaded already. `//kernel:sbsa_pkg_trust_no_root_test` boots without the boot-arg: the kernel refuses the good grant (`no package root`) and the probe stays refused.

## 5. Solver and store

- `ndpkg` embeds `libsolv` (BSD-3) for dependency resolution; the input is the manifests, the output a transaction plan written as JSON (`ndpkg plan --json`) before execution so an agent or human can review it.
- Store is content-addressed; two versions of a library coexist; `ndpkg gc` removes unreferenced entries. Activation is per-"view" (system view, per-user view) via bind mounts, which gives per-user package sets for free and lets a downstream show a process a curated package view.
- Each transaction begins with a ZFS snapshot of `ndpool/pkg`; power loss mid-transaction rolls back to the snapshot on next boot.

## 6. Kernel and kext updates

1. `ndpkg system upgrade` clones the active boot environment to a new dataset, installs the new `kernel` and kexts into it, runs `kcgen` → `kc.boot` written to the ESP under `/EFI/NeoDarwin/be/<be-name>/`, then snapshots the BE and marks it `next` in `boot.cfg`.
2. `neoboot` reads `boot.cfg` (`default`, `next`, `tries`). It decrements `tries`; once userland reaches `launchd` and `pkgd` marks boot-ok, `tries` is reset and `next` becomes `default`. Three failed tries boot the previous BE automatically.
3. Kexts declare `kernel-abi`; a kext for the wrong ABI cannot enter a collection. ABI is bumped only when the kernel's export list changes incompatibly (checked by `exports_list` diff in CI).
4. Auxiliary (non-boot) kexts and dexts are loaded post-boot from an `aux` collection rebuilt the same way; no dynamic single-kext loading on ARM64 (XNU disables it when booted from a fileset).

## 7. Third-party software: the ports tree

Third-party software comes from NeoDarwin's own ports tree (`ports.md`, decision 2026-09-29). A port is a recipe; building it produces an `.ndpkg` with `kind = "port"` and provenance (origin, recipe commit, upstream version, distfile digests, licence). Ports have their own repository index (`ports`) and key, the base never depends on a port, and GPL software ships only this way. FreeBSD ports and pkgsrc are import sources for recipes, not runtime dependencies.

## 7.1 Trust roots for downstreams

`ndpkg` can trust several key-chain roots. Each root is scoped to the package names or origins it may sign: NeoDarwin's root signs the base and the ports index; a downstream's root signs the downstream's packages and system sets; a machine's local key signs packages built there with `ndports`. A root cannot sign outside its scope, so adding a downstream repository cannot replace a base package (`downstream.md` §3).

## 8. Command surface and files

`ndpkg install|remove|upgrade|rollback|search|info|verify|gc|plan`, `ndpkg system status|switch|rollback`. Every command has `--json`. The installed state is plain files under `/var/db/ndpkg/installed/<name>/{manifest,files,state}`, and `pkgd` logs transactions as JSON lines to `/var/log/ndpkg.log`. A downstream can serve the same information in its own form (Magi publishes it under `/n/sys/pkg`).

## 9. Bootstrapping order

P2-01 format + `nd_package` rule → P2-02 store + activation → P2-03 system sets as ZFS boot environments (needs P3-03 root on ZFS) → P2-04 repositories + signing → P2-05 ports tree (ports.md §8) → P2-10 and P2-11 importers and bulk builds → P2-09 transparency log (optional).
