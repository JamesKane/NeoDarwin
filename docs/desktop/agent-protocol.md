# /n/agent: applications as file trees for AI agents

Version 1. Every native application in NeoDarwin that has state worth reading or actions worth taking serves a small 9P tree, mounted at `/n/agent/APPID`. An agent, local or in the cloud, reads the app's schema and state as files and drives it by writing command lines to a file. There is no accessibility tree to scrape and no screenshot to parse: the application publishes its own semantic model, and the same four files work for a text editor, a file manager, a mail client or the window server.

This is not new to Plan 9. acme has exposed its windows as `/mnt/acme/N/{addr,body,ctl,data,event,tag}` since 1993, and every acme extension ever written (`win`, `Mail`, `acme-lsp`) is an "agent" in the sense of this document. The protocol here standardises the pattern so agents can discover apps and read their schemas without per-app knowledge, and adds a JSON dialect that language models handle well.

Files in the repo:

| Path | Role |
|---|---|
| `docs/desktop/agent.h` | the protocol constants and the three callbacks an app implements |
| `libagent/agent.c` | a 9P2000 server that presents any app as the four files, about 400 lines |
| `cmd/agentedit/agentedit.c` | the example: an editor exposing cursor, selection and verbs |
| `tools/agentctl.py` | an agent-side 9P client for hosts without 9P, and the end-to-end demo |

> Built and run: the editor and library compile with `-Wall -Wextra -Wpedantic -Werror` and run clean under AddressSanitizer and UBSan. The demo drives the editor over a shell pipe and over a Unix socket: schema discovery, open_file, search, insert_text, get_lines, state, save, and the event log, with every reply checked.

## 1. The tree

```
/n/agent/
    index                r    one line per registered app: APPID PID NAME VERSION
    log                  r    registrations and departures, JSON lines
    APPID/
        schema           r    JSON: verbs, parameters, the shape of state and events
        state            r    JSON snapshot of the app's semantic state
        actions          rw   write a command line; read the reply on the same fd
        log              r    append-only JSON events; a read blocks until there is one
```

`APPID` is a short lowercase name (`edit`, `files`, `mail`, `wsys`). When several instances of one app run, they are `edit`, `edit.2`, `edit.3`; the `index` file gives the pid to tell them apart.

Each application serves its own subtree. On NeoDarwin it posts the service in `the `nsd` registry entry `agent.APPID`` and mounts it on `/n/agent/APPID`; the `agentd` registry serves `/n/agent` itself, creates the mount point when an app writes `register APPID` to its control file, and maintains `index` and `log`. Because mounts are per namespace, what an agent can see is exactly what its namespace contains: a sandboxed agent gets a namespace with only the apps it may touch, built with `bind` before it starts. That is the whole authorisation model, and it is the one every other Plan 9 program already lives under.

### schema

A JSON document, generated by the app, that an agent reads once. It names the app and version, describes the `state` object field by field, and lists the verbs with their parameters and types (`string`, `int`, `bool`, with `?` for optional), a one-sentence description, and the shape of the reply. It also describes the event objects that appear on `log`. The editor's schema is in the appendix; an agent that has read it knows everything it needs.

### state

A JSON snapshot of the app's semantic state: for an editor the path, dirty flag, cursor and selection, line count and the full text; for a file manager the current directory, its entries, the selection and the clipboard; for the window server the windows, their titles and geometry. Opening `state` takes the snapshot; reads at increasing offsets see that one snapshot however long they take, and a new open takes a new one. Every snapshot carries `seq`, the app's change counter, so an agent can tell whether anything happened between two reads without diffing them.

### actions

Write one command line, read the reply. The reply belongs to the fd that wrote the command, so several agents, or one agent with several open fds, never see each other's replies. This is the same per-fid conversation `/net/cs`, `/net/dns` and factotum use.

A command is `verb key=value key="json string"`: bare values for numbers and simple words, JSON string syntax with escapes for anything else. One write may carry several lines; each produces one reply line, in order. The reply is one JSON object per command: `{"ok":true,"verb":...,"seq":N,...}` with verb-specific fields, or `{"ok":false,"error":"text"}`. Errors are never silent and never abort the remaining lines.

From a shell on NeoDarwin the client is `echo` and `cat`:

```
echo 'search pattern=TODO' > /n/agent/edit/actions
cat /n/agent/edit/state | jq .cursor
```

From a program that wants the reply, open once, write, read:

```
fd = open("/n/agent/edit/actions", ORDWR);
write(fd, "insert_text text=\"done\\n\"\n", ...);
n = read(fd, reply, sizeof reply);   /* {"ok":true,"verb":"insert_text","seq":9,"cursor":{...}} */
```

### log

Append-only JSON event lines. A read returns every event since the fd's last read; if there is none it blocks until the app logs one, so an agent process can `read` in a loop and react. Opening `log` starts at the present: an agent sees what happens after it started watching, not history (that is what `state` is for). The app keeps the last 256 events; a reader that falls further behind skips forward and the gap is visible in the `seq` numbers. Events carry `seq`, `event`, and enough detail to update a model of the state without re-reading it: for the editor, the byte range and length of each change.

### Optimistic concurrency

Every reply and every state snapshot carries `seq`. A verb may take `if_seq=N`, and the app refuses with `{"ok":false,"error":"stale","seq":M}` if its counter has moved, which is how an agent that planned an edit against a snapshot avoids clobbering what a human typed in between. The editor example accepts it on every mutating verb.

## 2. Local and cloud agents

A local agent needs nothing: the tree is in its namespace. A shell script uses `echo` and `cat`; a Python or Lua agent under libposix uses `open`, `write`, `read` on the same paths. On a host without 9P in the kernel, `tools/agentctl.py` speaks 9P2000 directly to an app's Unix socket or pipe, which is how the demo runs on macOS.

A cloud agent gets the tree the way every remote Plan 9 program gets a file: `nsd` exports the agent's namespace (containing only the permitted `/n/agent/...` mounts) over TLS, authenticated by a `keyd` token, and the cloud side mounts it. The agent's code is identical; only its namespace differs. Nothing about the protocol is local-specific, and nothing about the application knows whether its caller is a shell, a local model or a remote one.

## 3. The example: agentedit

`agentedit` is an editor core with acme's addressing model: a UTF-8 buffer indexed by byte offset, with the cursor being a selection `[q0, q1)`. It implements the three callbacks `libagent` needs, in about 300 lines, and serves on a pipe (`-p`) or a Unix socket (`-u PATH`).

Verbs: `open_file path=`, `save [path=]`, `insert_text text= [at=]` (replaces the selection by default, cursor lands after the text), `delete [q0= q1=]`, `select q0= q1=` or `select line=`, `goto line=`, `search pattern= [from=] [all=1]` (selects the first match, or lists all with line and column), `replace pattern= with= [all=1]`, `get_lines from= to=`, `state`.

The demo transcript, from `tools/agentctl.py demo -p ./agentedit`:

```
ls /n/agent/edit -> ['schema', 'state', 'actions', 'log']
open_file   -> {"ok":true,"verb":"open_file","seq":1,"cursor":{"q0":0,"q1":0,"line":1,"col":1},"selection":"","dirty":false,"length":23}
search      -> {"ok":true,"verb":"search","seq":2,"cursor":{"q0":11,"q1":16,"line":2,"col":6},"selection":"gamma",...}
insert_text -> {"ok":true,"verb":"insert_text","seq":3,"cursor":{"q0":16,"q1":16,"line":2,"col":11},"dirty":true,...}
search miss -> {"ok":false,"error":"not found"}
search all  -> {"ok":true,"verb":"search","matches":[{"q0":0,"q1":1,"line":1,"col":1}, ... 4 matches]}
get_lines   -> {"ok":true,"verb":"get_lines","lines":["beta GAMMA","delta"]}
state       -> {"seq":3,"dirty":true,"lines":4,"cursor":{"q0":16,"q1":16,"line":2,"col":11}}
log         -> ['open', 'select', 'insert', 'save']      failed searches log nothing
```

A file manager follows the same pattern with a different vocabulary: `state` lists the directory, entries with size, mode and mtime, the selection and the clipboard; verbs are `cd path=`, `select names=`, `open name=`, `copy`, `cut`, `paste`, `rename name= to=`, `delete`, `mkdir name=`, `search pattern=`; events are `cd`, `select`, `change`. The window server's endpoint is its existing `/n/desktop` tree with a `schema` added.

## 4. Implementing an endpoint

An application provides three functions and calls `agent_serve` from a process or thread of its own:

```c
static const Agentops ops = { "edit", "1", schema, state, action };
Agent *ag = agent_new(&ops, &editor);
/* NeoDarwin: register the pipe with nsd as agent.edit; nsd mounts it on /n/agent/edit */
/* host:      agent_listen_unix("/tmp/edit.sock") + agent_accept_loop(ag, lfd) */
```

- `schema(ctx, buf, n)` writes the JSON schema and returns the length it needs.
- `state(ctx, buf, n)` writes a snapshot the same way. `libagent` calls it once per open.
- `action(ctx, line, reply, n)` runs one command and writes one JSON reply line.
- `agent_log(ag, line)` appends an event whenever state changes, from any code path, including the UI.

The library handles fids, snapshots, per-fid replies, blocked log readers and `Tflush`. The application never sees 9P. In a real GUI application the server loop runs in its own proc and the callbacks take the app's lock, exactly as acme's file server proc does.

## 5. Rules for schema and verb design

- **Verbs are what a user could do, named as the user would say it.** `open_file`, `search`, `insert_text`, not `dispatch_event`.
- **State is the model, not the view.** Byte offsets, paths, entries and flags; never pixel coordinates or widget ids.
- **Every mutation is idempotent given `if_seq`.** An agent can retry safely.
- **Replies echo the new cursor or selection.** Most agent loops are read state, act, check; the reply saves the second read.
- **Text is UTF-8 and offsets are bytes**, as in acme, so `get_lines` and `search` results line up with `insert_text at=`.
- **The log describes deltas.** `insert q0 q1 n` is enough to update a local copy of the buffer.

## 6. Open points

- `agentd` (the registry serving `index` and `log`) is an `nsd` plug-in (roadmap P5-01); the pilot's example apps mounted directly.
- Attach carries a `keyd` capability token; the namespace is still the authorisation model, the token is how `nsd` decides what to mount (namespaces design §4).
- The command syntax accepts JSON strings for values; a full JSON object form `{"verb":...,"args":{...}}` is reserved for version 2 and would be accepted on the same file.
- Long-running verbs (a search over a large tree, an import) return `{"ok":true,"job":N}` and report completion on `log`; the editor has none.
